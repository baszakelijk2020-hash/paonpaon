## Where we are

**Phase 0 (engineering foundation): done.** **Phase 1: in progress —
one slice shipped.**

### Shipped: PAON Admin — platform auth + retailer onboarding

A PAON platform operator can sign in to PAON Admin and onboard a new
retailer end to end:

- Sign in at `/login` (Supabase Auth, email + password).
- `middleware.ts` protects every route, refreshes the session, and
  rejects any signed-in user who isn't platform staff.
- `/retailers` lists tenants; `/retailers/new` creates one **and**
  invites its first owner (`role: "owner"`) in the same submission —
  see `docs/DECISIONS.md` ADR-009 for why invite-then-persist is the
  required order.
- `/retailers/[id]` shows the tenant and its staff, with an
  Invited/Active badge per staff member.

Everything after `getSession()` is checked twice: once in
`middleware.ts` (routing), once in each protected layout/page/Server
Action via `@paon/auth` guards (`requirePlatformSession`,
`requirePlatformOperator`) — defense in depth per
`docs/ARCHITECTURE.md` "Authorization Model". The real boundary is
Postgres RLS (`supabase/migrations/20260719000002_*`,
`20260719000003_*`).

### Not yet built (the rest of Phase 1)

In priority order — pick up here:

1. **Retailer onboarding acceptance** — the invited owner clicks the

3. **First employee** — invite flow for additional retailer staff,
   run from _inside_ Retailer Portal this time (today only PAON Admin

   Server Action yet).
4. Then: brand configuration, product catalogue, customer
   registration/Customer Portal auth, and onward per
   [ROADMAP.md](./ROADMAP.md).

## Environment constraints this session hit

Record these so the next session doesn't waste time rediscovering them:

- **No Docker daemon available in the sandbox this was built in.**
  `supabase start` could not be run locally, so:
  - Every migration and RLS policy was written and reviewed by hand,
    not executed against a live Postgres instance.
  - `packages/database/src/generated/database.types.ts` is hand-
    maintained to match the migrations (see the file's own header
    comment) rather than generated by `supabase gen types`. **Run
    `pnpm --filter @paon/database generate-types` against a real local
    instance and diff it against the hand-written version at the first
    opportunity** — that's the highest-value verification gap right
    now.
  - The Playwright e2e specs (`apps/admin/e2e/*.spec.ts`) were written
    and typechecked but never executed — they depend on a live
    Supabase instance via `e2e/global-setup.ts`. They run in CI
    (`.github/workflows/ci.yml`, `e2e` job, which has Docker), but
    have not been observed passing yet. Treat their first CI run as
    the real verification, and fix forward if anything doesn't match
    reality (cookie handling, RLS policy typos, etc. are the likely
    failure modes for code that's only been typechecked, not run).
  - What _was_ verified locally, repeatedly, and is trustworthy:
    `pnpm lint`, `pnpm typecheck`, `pnpm test` (unit), `pnpm build`,
    `pnpm format:check` — all green across every package and app.
- **No live Supabase project.** `.env.local` was never created in this
  session. To actually run the app: `supabase start`, copy its printed
  `API URL`/`anon key`/`service_role key` into each app's `.env.local`
  per `.env.example`, then `pnpm --filter @paon/database
bootstrap:platform-admin` (see that script's header comment) to
  create the first PAON Admin login before `pnpm dev`.

## Conventions established this slice (reuse, don't reinvent)

- **JWT claim sync via trigger**: any new staff-like table that needs
  its role visible to RLS follows `sync_platform_role_claim`/
  `sync_retailer_staff_claim` in the two staff-table migrations —
  `security definer` trigger mirrors role (and clears it on
  delete/unlink) onto `auth.users.raw_app_meta_data`.
- **`PaonSupabaseClient`** (`packages/database/src/client-type.ts`) is
  the only type every repository and client factory should use for a
  Supabase client parameter — see `docs/DECISIONS.md` ADR-010 before
  reaching for `SupabaseClient<Database>` directly again.
- **`stripUndefined`** (`@paon/utils`) at the Server Action boundary,
  right after parsing a zod schema, before passing the result to a
  repository — see ADR-011.
- **Server Action forms use `useActionState`** with a
  `{ values, fieldErrors, formError }` state shape (see
  `apps/admin/app/(dashboard)/retailers/new/actions.ts` +
  `retailer-form.tsx`) — this is now the template for every future
  form in every app, not just this one.
- **`@paon/ui` gained**: `Input`, `Label`, `Select`, `FormField`,
  `Card`, `Badge`. Reach for these before adding a new primitive.
